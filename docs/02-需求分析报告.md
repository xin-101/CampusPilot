# CampusPilot 需求分析报告

## 一、比赛需求分析

### 1.1 赛事背景
本项目用于参加AI Agent创新类高校竞赛，重点考察学生的AI技术应用能力、问题解决能力和工程实践能力。

### 1.2 评分标准分析

#### 智能体设计方案书（30%）
- **要求**：智能体设计完整性、逻辑性、技术可行性
- **应对**：提供完整的Agent架构设计，包括角色分工、能力定义、交互流程
- **重点**：体现从简单问答到复杂任务执行的完整能力

#### 路演答辩（30%）
- **要求**：PPT逻辑、美观度、演示流畅性、答辩专业性
- **应对**：设计清晰的演示脚本，准备专业的答辩材料
- **重点**：展示Agent的完整执行过程和实际效果

#### 创新性（15%）
- **要求**：Agent技术创新、行业应用创新、解决传统痛点
- **应对**：突出复杂度自适应、主动服务、政策时效感知等创新点
- **重点**：强调从问答到执行的范式转变

#### 应用价值（15%）
- **要求**：场景真实性、场景匹配度、减负增效、可推广性
- **应对**：聚焦真实校园场景，提供量化效果数据
- **重点**：展示对学生和学校的实际价值

#### 作品优化效果（10%）
- **要求**：省赛到决赛的优化、功能拓展、落地可行性
- **应对**：设计清晰的升级路线，从基础功能到高级功能
- **重点**：展示持续迭代和优化能力

#### 团队协作与潜力（10%）
- **要求**：团队分工、问题解决能力、后续迭代、落地规划
- **应对**：明确团队分工，制定详细开发计划
- **重点**：展示团队执行力和项目可持续性

### 1.3 平台要求
- **主要平台**：SF-FastGPT作为核心Agent搭建与Workflow编排平台
- **辅助平台**：超星AI能力中心、百川云璟数据集
- **技术栈**：Java Spring Boot + Vue 3 + MySQL + Docker

## 二、用户需求分析

### 2.1 核心用户画像

#### 主要用户：学生
- **年级**：大一至大四本科生
- **特点**：熟悉互联网，习惯移动端服务
- **痛点**：信息分散、流程复杂、容易遗漏
- **期望**：一站式服务、智能指导、主动提醒

#### 次要用户：辅导员
- **职责**：学生管理、事务指导、信息传达
- **痛点**：重复咨询多、信息同步慢、工作量大
- **期望**：减少重复工作、提高管理效率

#### 潜在用户：教务老师、学工部门
- **职责**：政策制定、事务办理、数据统计
- **痛点**：咨询量大、信息不准确、统计困难
- **期望**：自动化处理、准确信息、数据可视化

### 2.2 用户场景分析

#### 场景1：奖学金申请
- **用户**：大三学生小王
- **需求**：想申请国家奖学金，但不知道具体要求
- **传统流程**：搜索政策→咨询辅导员→准备材料→提交申请→等待结果
- **期望流程**：告诉AI想申请→AI自动判断资格→生成材料清单→创建待办→跟踪进度

#### 场景2：请假办理
- **用户**：大二学生小李
- **需求**：需要请病假，但不知道流程
- **传统流程**：查找请假制度→准备证明材料→找辅导员签字→提交教务处
- **期望流程**：告诉AI请假原因→AI自动判断流程→生成所需材料→创建待办→提醒销假

#### 场景3：宿舍报修
- **用户**：大一学生小张
- **需求**：宿舍空调坏了，需要报修
- **传统流程**：查找报修电话→打电话报修→等待维修→确认完成
- **期望流程**：告诉AI设备故障→AI自动创建报修工单→跟踪维修进度→提醒确认

#### 场景4：成绩查询
- **用户**：大四学生小陈
- **需求**：想了解自己是否满足保研成绩要求
- **传统流程**：登录教务系统→查询成绩→计算绩点→对比保研要求
- **期望流程**：问AI保研成绩要求→AI自动获取成绩→计算绩点→对比要求→给出建议

### 2.3 用户需求层次

#### 基础需求（Must Have）
- 政策信息查询
- 基础事务办理指导
- 学生信息查看
- 待办事项管理

#### 期望需求（Should Have）
- 智能资格判断
- 材料清单生成
- 办理进度跟踪
- 主动提醒服务

#### 兴奋需求（Nice to Have）
- 复杂度自适应
- 多轮对话上下文
- 个性化建议
- 数据分析看板

## 三、业务需求分析

### 3.1 核心业务场景

#### 3.1.1 奖学金/资助
- **政策类型**：国家奖学金、国家励志奖学金、国家助学金
- **功能需求**：
  - 政策查询与对比
  - 资格条件判断
  - 材料清单生成
  - 申请流程指导
  - 截止日期提醒
- **复杂度**：高（涉及多条件判断、多材料准备）

#### 3.1.2 请假管理
- **请假类型**：病假、事假、公假
- **功能需求**：
  - 请假制度查询
  - 请假流程指导
  - 材料要求说明
  - 审批流程跟踪
  - 销假提醒
- **复杂度**：中（流程相对固定，但需要状态跟踪）

#### 3.1.3 考试/教务
- **事务类型**：考试安排、补考申请、重修办理、成绩查询、学籍变更
- **功能需求**：
  - 考试信息查询
  - 补考/重修政策
  - 办理流程指导
  - 材料准备说明
- **复杂度**：中（信息查询为主，部分需要办理）

#### 3.1.4 宿舍/校园生活
- **事务类型**：宿舍报修、晚归登记、宿舍调换、校园卡服务
- **功能需求**：
  - 报修流程指导
  - 管理制度查询
  - 服务申请办理
  - 进度跟踪
- **复杂度**：低-中（流程相对简单）

#### 3.1.5 学生证明
- **证明类型**：在读证明、成绩证明、学籍证明、获奖证明
- **功能需求**：
  - 证明类型说明
  - 办理流程指导
  - 材料要求
  - 办理地点和时间
- **复杂度**：低（主要是信息查询）

### 3.2 业务规则分析

#### 政策时效规则
- 政策有明确的生效时间和失效时间
- 新政策发布后，旧政策自动失效
- 过渡期政策需要特殊处理
- 不同年级学生可能适用不同政策

#### 权限控制规则
- 学生只能访问自己的信息
- 辅导员可以查看授权范围内学生
- 管理员可以查看所有数据
- 敏感操作需要二次确认

#### 流程状态规则
- 事务有明确的生命周期
- 状态变更需要记录日志
- 异常状态需要特殊处理
- 超时状态需要自动提醒

### 3.3 数据需求分析

#### 学生数据
- 基本信息：姓名、学号、年级、专业、班级
- 学业信息：成绩、绩点、学籍状态
- 事务信息：待办、申请、进度

#### 政策数据
- 政策内容：名称、分类、条款、附件
- 政策属性：发布部门、时间、版本、状态
- 政策关系：适用对象、条件、材料要求

#### 事务数据
- 事务定义：类型、流程、规则、时限
- 事务实例：申请、办理、完成、归档
- 事务日志：操作记录、状态变更、异常处理

## 四、技术需求分析

### 4.1 功能性需求

#### 4.1.1 Agent能力需求
- **意图识别**：准确识别用户自然语言需求
- **知识检索**：从政策知识库中准确检索相关信息
- **条件判断**：根据学生信息判断是否满足条件
- **流程规划**：自动生成事务办理流程
- **工具调用**：调用后端API获取数据和执行操作
- **任务跟踪**：跟踪事务办理进度
- **主动提醒**：主动发现并提醒未完成事项

#### 4.1.2 系统功能需求
- **用户管理**：登录、注册、权限控制
- **学生服务**：信息查询、事务办理、进度跟踪
- **政策管理**：知识库维护、版本管理、时效控制
- **任务管理**：待办创建、状态跟踪、提醒通知
- **数据统计**：使用统计、效果分析、满意度调查

### 4.2 非功能性需求

#### 4.2.1 性能需求
- **响应时间**：简单问答 < 2秒，复杂任务 < 10秒
- **并发能力**：支持100+并发用户
- **系统可用性**：99.9%可用性

#### 4.2.2 安全需求
- **身份认证**：JWT Token认证
- **权限控制**：基于角色的访问控制
- **数据安全**：敏感信息加密存储
- **操作审计**：关键操作日志记录

#### 4.2.3 可用性需求
- **界面友好**：现代UI设计，操作直观
- **响应式**：支持PC和移动端访问
- **国际化**：预留多语言支持

#### 4.2.4 可维护性需求
- **代码规范**：遵循编码规范，注释清晰
- **模块化**：组件化设计，低耦合高内聚
- **文档完整**：提供完整的开发和运维文档

### 4.3 技术约束

#### 平台约束
- **Agent平台**：SF-FastGPT
- **后端框架**：Spring Boot 3.x
- **前端框架**：Vue 3 + Element Plus
- **数据库**：MySQL 8
- **部署方式**：Docker容器化

#### 开发约束
- **开发周期**：分阶段开发，Phase 0-8
- **团队规模**：小型团队，需要高效协作
- **测试要求**：完整的测试体系和测试报告
